# Vercel frontend + Render backend

The default `render.yaml` now creates four Free web services and asks for external
Neon PostgreSQL and CloudAMQP URLs. The paid setup below uses `render.paid.yaml`.

This is a **demo with simulated payment and shipping providers**, not a public production commerce system. No real customer or payment data should be entered.

## Access protection is a release gate

The four Render APIs require a shared server-to-server token. Only `GET /health` is public. The Vercel server sends the token; it is never a `NEXT_PUBLIC_*` variable or a browser credential.

**That token does not protect the Vercel application from visitors.** Before sharing a hosted URL, protect the entire Vercel deployment, including `/api/*`, using deployment protection that covers the production domain, or implement the agreed demo-password gate. Do not assume that protection of preview deployments also protects production. The choice of a shared demo password versus a public demo is awaiting confirmation.

Do not enable a public deployment until that decision is resolved. This project has no individual accounts, roles, ownership checks, authoritative pricing, or public abuse controls.

## 1. Verify locally

Use Node 24 (`.nvmrc`) and Docker:

```sh
npm ci
npx playwright install chromium
docker compose up -d --wait
PLAYWRIGHT_PORT=3114 npm run verify:release
npm audit --omit=dev --audit-level=high
docker build -f Dockerfile.backend -t saga-backend:release .
```

Backend tests use `TEST_PAYMENT_DATABASE_URL`, `TEST_INVENTORY_DATABASE_URL`, `TEST_SHIPPING_DATABASE_URL`, `TEST_ORDER_DATABASE_URL`, and `TEST_RABBITMQ_URL`, or the existing service `.env` files. Copy the service examples for local use only. Tests create and remove their own databases, queues, and broker container; they must never target production infrastructure. The database test user needs permission to create databases.

`verify:release` builds once, runs backend/database/recovery tests, real browser-to-backend checkout tests, UI/state/API tests, desktop/mobile browser tests, and the live Next.js proxy integration test. The GitHub Actions workflow performs these checks on Node 24.

## 2. Optional paid Render deployment

1. Push the reviewed code to your Git repository.
2. Create a Blueprint in Render using `render.paid.yaml`. Review the estimated charges before approving it: this creates **four paid web services, four paid PostgreSQL instances, and one paid RabbitMQ private service with a disk**. It is not a free-tier deployment.
3. Keep all resources in the same region (the supplied configuration uses Singapore). Database external connections are disabled, and RabbitMQ has no public endpoint.
4. The Blueprint builds `Dockerfile.backend`, runs each service's migrations before deployment, and seeds inventory without replenishing existing stock.
5. RabbitMQ credentials and `BACKEND_API_TOKEN` are generated by Render. The startup wrapper safely builds the AMQP URL from separate values, including URL-encoding the generated password.
6. Save the HTTPS URLs of `saga-orders`, `saga-payment`, `saga-inventory`, and `saga-shipping`. Obtain the generated `BACKEND_API_TOKEN` from the `saga-backend-auth` environment group.
7. Verify each `/health` returns 200, business endpoints reject requests without the token with 401, and authenticated `/ready` returns 200.

The platform health check intentionally uses liveness (`/health`), not authenticated readiness. Use the application's Services page to verify database, broker, and recovery readiness. A green Render process status alone is not proof that orders can complete.

Auto-deployment is off for backend services. Deploy a reviewed commit after checks pass; coordinate contract and migration changes across services. No cloud resources are created by merely adding these files.

## 3. Deploy Vercel

Import the same repository:

| Setting | Value |
| --- | --- |
| Framework | Next.js |
| Root Directory | `apps/web` |
| Include source files outside Root Directory | Enabled |
| Node.js | `24.x` |
| Install/build | Supplied by `apps/web/vercel.json` |
| Output directory | Next.js default; do not use static export |

Set these **server-only** environment variables for the intended deployment environment:

| Variable | Value |
| --- | --- |
| `ORDERS_SERVICE_URL` | HTTPS origin of `saga-orders` |
| `PAYMENT_SERVICE_URL` | HTTPS origin of `saga-payment` |
| `INVENTORY_SERVICE_URL` | HTTPS origin of `saga-inventory` |
| `SHIPPING_SERVICE_URL` | HTTPS origin of `saga-shipping` |
| `BACKEND_API_TOKEN` | Same token as all four Render services |
| `BACKEND_TIMEOUT_MS` | `10000` |

Use origins only, without API paths or embedded credentials. Vercel functions cannot use Render private hostnames, so these are the authenticated public HTTPS origins. The browser calls same-origin `/api/*`; CORS changes are not needed.

Resolve the access-protection gate above before publishing. Do not connect untrusted preview builds to the shared demo backend; use separate credentials/infrastructure for previews or leave their backend configuration unset. Redeploy Vercel after changing environment variables.

## 4. Hosted smoke check

Local tests cannot prove a deployment in an account that has not been provisioned. After both platforms are deployed:

- An unauthenticated visitor must be denied access to private pages **and API routes**, including the production/custom domains.
- All four services must show ready in the UI.
- Submit a Demo Keyboard order: confirm COMPLETED, CHARGED, finalized inventory and CREATED shipment.
- Submit a Demo Monitor order (seeded stock is zero): confirm FAILED only after REFUNDED.
- Refresh both order URLs and verify fresh status; terminal orders must offer no Resume button.
- Check the mobile navigation, order history, attention queue, and independent participant sections.
- Restart only the demo broker and confirm readiness turns unhealthy, pending orders remain durable, and processing recovers. Never use fault-injection checks on a system containing valuable data.

## Operations and limits

- Keep all secrets in platform environment settings. Rotate the backend token on all four services and Vercel together; mixed values temporarily return 401.
- Use fake demo data. The most recent 100 attention records are shown; this is not a complete operational backlog viewer.
- Back up PostgreSQL and RabbitMQ before destructive maintenance. Do not drop tables, reset volumes, or rerun seeds to restore consumed stock.
- RabbitMQ uses one persistent node and is not highly available. Disk-backed broker deployments can interrupt processing; the outbox/recovery flow is designed to resume afterward.
- Application rollback does not roll back database migrations. Prefer backward-compatible migrations and inspect compatibility before reverting a deployment.
- Avoid free services that sleep while background consumers/recovery workers need to run.
- Do not represent the demo as a production payment/shipping integration or a production-ready public store.

## Optional local-only deployment

`docker compose -f compose.demo.yml up --build -d --wait` starts a separate local demo and exposes only `127.0.0.1:3004`. Use `DEMO_WEB_PORT` if that port is occupied. Its fixed credentials are suitable only for isolated local use; **do not reuse this Compose file for public hosting**. Stop it with `docker compose -f compose.demo.yml down`; volumes remain intact.
